# 微信小程序版执行计划

> 前置文档：`docs/requirements.md`（PC 端需求 v0.1）
> 本文档回答一个问题：**把这个工具做成小程序，要改什么、怎么做、按什么顺序做。**

---

## 0. 先说结论

小程序不是"给桌面工具换个皮"。它把产品形态从**归档器**变成了**采集端**，原因很硬：小程序无法访问本地文件系统，也无法长期保存文件。

所以正确的定位是：

> **小程序 = 随手收票 + 录入 + 随身查台账。**
> **长期归档 = 云端存储 + 定期导出（或后续接一个 PC 侧归档端）。**

原来的四级解析链路依然成立，只是**执行位置要从"本机"重新分配到"端侧 / 云函数"**。

---

## 1. 五个硬约束，先接受再设计

| # | 约束 | 后果 | 对策 |
|---|---|---|---|
| C1 | **导入路径唯一**：只能 `wx.chooseMessageFile` 从微信会话选文件，够不到手机本地目录 | 用户必须先把发票发到「文件传输助手」 | 首屏写清引导，这是唯一路径，别想着绕 |
| C2 | `wx.setStorageSync` **总量 10MB、单 key 1MB** | 台账放不进去 | 台账写**私有目录**（`USER_DATA_PATH`，约 200MB），Storage 只放配置 |
| C3 | 云端跑不了 PaddleOCR（小程序端也没有模型） | OCR 只能调外部 API | **已砍**（D2），见 §8 |
| C4 | **个人主体不能选「工具-发票查询」类目**（官方备案指引明示"个人主体不可从事"） | 想发布上线会被类目卡住 | **自用不发布，走体验版**——见下 |
| C5 | 端侧**提不了 PDF 文本层** | L3 路径基本失效 | 只保留 XML / OFD / 图片，PDF 只存不解析 |

> **关于 C2 的一个常见误解**：很多人以为"小程序只能存 10MB"，那是 `setStorageSync` 的 key-value 配额。小程序还有一个**私有文件目录** `wx.env.USER_DATA_PATH`，容量约 200MB，可以正常读写二进制文件。
> **"原件存本地"这个方案能成立，靠的就是这个目录。** 这也是为什么 D3 选本地之后，连云开发都不需要了。

### 关于 C4——这是本计划最省事的一环

个人自用**根本不需要发布**：

- 用**开发版 / 体验版**，添加自己为体验成员，扫码即用，**跳过审核、跳过 ICP 备案、跳过类目**。
- 唯一代价：只有你和体验成员能用（上限 15 人），不能分享给陌生人。
- 如果哪天要公开发布，再选 `工具 > 记账`（个人可选类目），并且**文案里绝对不能出现"发票查验 / 真伪校验"字样**，否则类目不匹配直接拒。

> 建议：**先按体验版做，别为了"上线"提前折腾备案和类目。**

## 2. 架构选型

| 方案 | 组成 | 优点 | 代价 |
|---|---|---|---|
| **A. 纯小程序 + 云开发**（推荐起步） | 小程序 + 云函数 + 云数据库 + 云存储 | 零服务器、零备案、零运维；云函数免域名白名单 | 数据在腾讯云；按量计费（自用量极小） |
| B. 小程序 + 自建 Go 后端 | 复用一个 Go 服务 | 数据完全自控；能复用 PC 端解析代码 | 需**已备案域名 + HTTPS**，小程序 request 白名单强制；个人办备案要 7–15 工作日 |
| C. 小程序 + PC 归档端 | A + PC 端（原 Go 工具）定期同步 | 兼顾采集便利与 10 年归档合规 | 工作量约翻倍 |

**建议路线：A 起步 → 保留"一键导出全量原件 zip"通道 → 有归档刚需时再补 C 的 PC 端。**

理由：B 的备案成本对自用工具完全不划算；C 可以后置，因为导出功能本身就是 C 的最小实现。

> **最终结论**：按 D3 决策（原件存本地）收敛后，比方案 A 还要轻——**连云开发都不需要**，纯端侧即可。见 §8。

## 3. 端侧分工（核心表）

> 按 D3 决策（原件存本地）已收敛为**纯端侧**，无云开发、无云函数、无计费。

这张表决定了每一块代码写在哪，是后续所有任务的基础。

| 能力 | 执行位置 | 依赖 | 备注 |
|---|---|---|---|
| 扫发票二维码 | 端 · `wx.scanCode` | 原生 | 需先配隐私协议 |
| 二维码解析（明文串） | 端 | 无 | 纯字符串运算；**CRC 只记录不校验**，算法非标准（S1 实测） |
| **XML 解析** | 端 · `readFile` | 无 | ★ 最准、零成本、数据不出手机 |
| OFD 目录结构 | 端 | 无 | 读 ZIP 中央目录，零依赖 |
| OFD 文本层 | 端 | pako（解 deflate） | M0 先验证结构，再决定是否引入 |
| PDF | 端，能力有限 | 不引入 pdf.js | 只存不解析，字段靠二维码补 |
| 图片 OCR | **不做** | — | 已砍（D2） |
| 去重 / 金额勾稽 / 号码校验 | 端 | 无 | 数据量小 |
| 原件存储 | 端 · `USER_DATA_PATH` | — | 30 天 TTL |
| 台账存储 | 端 · JSON 分片 | — | Storage 只放配置 |

> **全部端侧的代价**：数据只在这台手机上，换机、卸载、清缓存即丢。所以**导出从可选功能变成必备功能**，M5 要提前做。

## 4. 里程碑

### M0 · 技术验证（先做这个，别写 UI）

**目标**：用最短时间证伪，避免在错误假设上堆代码。
**产出**：`docs/spike.md`，每条都有明确结论。

| # | 验证项 | 怎么验 | 若失败的应对 |
|---|---|---|---|
| S1 | 数电票二维码扫出来到底是什么 | 真机 `wx.scanCode`，扫 3 类票：数电票打印件、老版电子普票、铁路/航空票，记录 `result` 原文与 URL 参数 | 若为纯加密链接且无可用字段 → 二维码降级为"仅存档"，主入口改为文件导入 |

| S3 | 端侧能否解析 XML | `readFile` + 正则抠字段，并 **dump 全部标签名**校准映射表 | 若不稳定 → 引入 `fast-xml-parser`，或退化为纯文本匹配 |
| S4 | OFD 是否标准 ZIP 且带文本层 | 端侧读 ZIP 中央目录，看有无 `Content.xml`；签章看 `Signs/` **或** `Annots/` | 无 `Content.xml` → OFD 只存不解析 |
| S5 | 本地私有目录容量与 TTL 清理 | 写 5MB 文件、递归统计目录、按 `mtime` 清理 30 天前文件 | 容量不足 → 缩短 TTL 或按数量上限裁剪 |

**验收**：5 条全部有"可行/不可行/替代方案"的结论。**S1 和 S3 结果直接决定要不要继续。**

> **状态：已完成（2026-11-16）**。S1/S2/S3/S4/S5 全部在真机跑通，结论逐条记录在 `docs/spike.md`。
> 两项计划被实测推翻：① 数电票二维码是明文串不是加密链接；② OFD 签章在 `Annots/` 而非必须在 `Signs/`。
> 一项被放弃：CRC16 校验（70 组变体均不匹配）。M0 通过，可以进入 M1。

### M4 ·（已取消）影像兜底

按 D2 决策砍掉 OCR。原因：小程序端跑不了模型，唯一路径是调第三方 OCR API，会重新引入「图片外传」和「按次计费」，与此项目的自用定位不符。

若将来真有大量"只有照片"的票，再单独评估。**不做 OCR 的兜底方案是**：这类票手动录入，4 个关键字段 30 秒能敲完。

### P0 · 导航重构 + 分类标签 + 待复核（2026-11-16 代码完成）

| 项 | 实现 | 说明 |
|---|---|---|
| 底部导航 | `app.json` tabBar：台账 / 统计 / 收票 / 设置 | 收票从台账底部按钮堆里拆出来独立成页；导出移到收票与设置页 |

四页都只做数据组装与事件转发；聚合逻辑在 `stats.js`，原因汇总在 `review.js`，文案映射在 `labels.js`。

`store.normalize()` 为老记录补默认 `category='未分类'`，因此既有台账不需要迁移。
`reviewList()` 只提示字段缺口，不做真伪判断。

**验收**：tabBar 四页可切换；XML 导入后分类自动预填且能按分类筛选；扫码草稿和异常票出现在待复核清单，点开可补录。

### P0 补充 · 批量连续扫码（2026-11-16）

同事的需求：同一台手机、一次扫一大批二维码、只取二维码里的字段、扫完导出到电脑。
确认不做场次隔离，因此不新增页面、不引入批次概念，只在收票页加一个入口。

- `utils/scanbatch.js`：连续调用 `collect.scanDraft()`，扫到用户取消为止；每张 toast 计数 + 轻震动；
  无法识别的二维码提示后继续，相机等真失败则停下，避免死循环。
- **退出交互（16:08 优化）**：`wx.scanCode` 是微信原生界面，不能加按钮，左上角 × / 手机返回键是唯一原生退出方式。
  因此进入前用 `notice()` 说明退出方法；每张 toast 带上「点左上角×结束」；每 10 张用 `askContinue()`
  弹一次「继续扫 / 结束」，给找不到 × 的用户一个明确出口，同时不回到逐张确认的低效模式。
- **重复即时提示（16:12）**：扫到一张后立刻用 `store.dedupeKey`（号码+日期+金额）查重，
  同时查本批次 `seen` 和台账 `findDuplicate`。命中就弹窗说明「本批次前面 / 台账里」，
  由用户选「仍然收下 / 跳过」。本批次没落库的那份只能靠 `seen` 识别，这是关键。
  `store` 导出 `dedupeKey` 复用同一判重口径，不在扫码侧重写键规则。
- 收票页「批量连续扫码」按钮：扫完给草稿打 `batch_id`，`batch.saveAll()` 落库，`batchmark` 记住该 id，弹窗显示入库汇总并询问是否去导出页。
- 导出页默认范围 = 最后一次批量扫码（`batchmark.current()`），没有标记时退回「全部」。
- 导出页支持两层自定义：
  - **范围**：本次扫码 / 全部 / 指定月份 / 自定义勾选（发票列表逐张勾选）；
  - **内容**：台账 CSV / 原件清单 CSV / 原件文件，可多选，按勾选顺序逐个转发，取消即停。
- **导出中断修复（16:19）**：真机勾了三项导出，第一个 CSV 显示「已发送、进入聊天」浮层时，
  紧跟着自动调第二次 `shareFileMessage` 被微信拒绝（`fail can not ...`）。
  改为每个文件发送前先弹确认框（带 `i/n` 序号），提示用户先关掉上个浮层再点确定，取消即停。
- 二维码字段边界不变：只有号码、金额、日期、票种、校验码；销方/税额/明细仍需文件导入。

**验收**：点批量连续扫码 → 连续扫多张无需逐张确认 → 点取消结束 → 进导出页默认就是本次扫码 → 可切范围并勾选内容 → 逐个转发到电脑。

### P0 补充 · 台账清理（2026-11-16）

用户要能清理旧票：长按列表弹操作、自定义勾选删除、按导入时间段删除。

- **原件事实**：扫码票没有原件（二维码只有文本，无文件）；只有 XML/OFD/PDF 文件导入才存原件到私有目录。
  因此删除一律沿用详情页口径：**只删台账记录，不删原件**，原件走导出页转发或 30 天 TTL 清理。
- 台账页卡片加 `bindlongpress`，`wx.showActionSheet` 给「查看详情 / 编辑 / 删除这张」，删除前二次确认。
- 台账页快捷区加「清理台账」入口 → `pages/manage/manage`：
  - 自定义勾选：全量列表勾选 → 删除所选；
  - 按导入时间：起止 `date` picker → 先预览命中张数与金额 → 确认删除。按 `created_at` 算，不是开票日期。
- `utils/purge.js` 承载区间筛选 / 删除 / 卡片转换，页面只做事件转发。

**验收**：长按一张票能删除；清理页勾选几张删除；选一个日期区间，预览数量正确，确认后只剩区间外的票。

## 5. 数电票 XML 结构（S3 真机已校验：63 条路径）

> 2026-11-16 用 `dzfp_26932000001295659876_20260802160711.xml`（4304 字节，`encoding="utf-8"`，无 BOM）实读确认。
> 完整树见 `docs/spike.md` §S3。这里列出**代码实际依赖的字段路径**。

```
EInvoice
├─ Header
│  ├─ EIid, Version, EInvoiceTag
│  └─ InherentLabel
│     ├─ GeneralOrSpecialVAT/LabelName      → 普通发票（LabelCode 02）
│     ├─ EInvoiceType/LabelName
│     ├─ InIssuType/LabelCode               → Y=蓝字 / N=红字（LabelName 只是字段名）
│     └─ TaxpayerType/LabelName             → 一般纳税人（Code 1）
├─ EInvoiceData
│  ├─ SellerInformation
│  │  └─ SellerName, SellerIdNum, SellerAddr, SellerTelNum,
│  │     SellerBankName, SellerBankAccNum
│  ├─ BuyerInformation
│  │  └─ BuyerName                          （个人抬头无 BuyerIdNum）
│  ├─ BasicInformation
│  │  └─ Drawer, RequestTime,
│  │     TotalAmWithoutTax, TotalTaxAm,
│  │     TotalTax-includedAmount,           ★ 带连字符
│  │     TotalTax-includedAmountInChinese
│  ├─ IssuItemInformation                   ★ 可重复
│  │  └─ ItemName, TaxClassificationCode, TaxRate,
│  │     Amount, ComTaxAm,
│  │     TotaltaxIncludedAmount             ★ 小写 t，与上面只差大小写/连字符
│  ├─ SpecificInformation
│  └─ AdditionalInformation
├─ TaxSupervisionInfo
│  ├─ InvoiceNumber                         20 位
│  └─ IssueTime                             ★ 开票日期在这里，不在 BasicInformation
├─ SellerAuthentication/AuthenticationMethods
└─ TaxBureauSignature
   └─ SignatureAlgorithm, SignatureFormat, SignatureTime, SignatureValue,
      KeyInfo, Reference
```

### 三个不可模糊匹配的字段

| 字段 | 正确路径 | 若模糊匹配会怎样 |
|---|---|---|
| 价税合计 | `BasicInformation/TotalTax-includedAmount` | 会命中明细行 `TotaltaxIncludedAmount`；单行明细时数值恰好相等，**错误被掩盖** |
| 开票日期 | `TaxSupervisionInfo/IssueTime` | 会取到 `BasicInformation/RequestTime`（申请时间） |
| 票种 | `.../GeneralOrSpecialVAT/LabelName` | 取到容器 XML 串，不是"普通发票" |

`miniprogram/utils/einvoice.js` 已按完整路径实现（`parseXml → getText/getAll → extractInvoice`），并通过 60 项断言回归测试。
`BuyerIdNum` 在个人抬头下缺失属正常，不进 `missing` 告警。

另两个实测细节：`InIssuType.LabelName` 是字段名「是否蓝字发票标志」而不是状态文本，状态看 `LabelCode`（`Y/N`），代码已归一化为 `isBlue`；`SignatureAlgorithm` 是 OID `1.2.156.10197.1.501`（SM2），`SignatureFormat` 为 `DETACH`，代码已映射为可读名。

### 可信度边界

`TaxBureauSignature` 存在 ≠ 已验真，**不存在**也不再当作硬性异常——OFD 侧签章可能在 `Annots/` 而非 `Signs/`（S4 实测）。
只把它当"结构完整性信号"打标，**绝不**对外宣称"已验证"。

## 6. 本地数据文件结构

```
USER_DATA_PATH/
└── invoices/
    ├── ledger/
    │   ├── 2026-11.json        # 当月记录分片
    │   └── 2026-10.json
    ├── files/
    │   └── {hash8}_{原文件名}    # 原件，30 天 TTL
    └── index.json              # 全局索引：发票号 → 分片，用于去重
```

单个分片文件的结构：

```js
{
  invoices: [{
    id,
    invoice_no, invoice_code,
    invoice_type,               // 数电票/电子专票/电子普票/铁路/航空
    issue_date,                 // 'YYYY-MM-DD'
    seller_name, seller_tax_id,
    buyer_name,  buyer_tax_id,
    amount_excl_tax_cent, tax_cent, total_cent,   // 整数分
    tax_rate,
    status,                     // normal | unknown | manually_verified
    verified_at,
    source,                     // xml | ofd | pdf | qr | manual
    confidence,
    raw_qr, qr_integrity,       // ok | failed | n/a
    anomaly: [],
    edited_fields: [],
    files: [{ name, path, size, digest }],
    note,
    created_at, updated_at
  }],
  items: [{
    invoice_id, line_no, name, spec, unit,
    quantity, unit_price_cent, amount_cent, tax_rate, tax_cent
  }]
}
```

> 为什么不像 CloudBase 那样拆三张表：本地没有查询引擎，拆表反而要写关联逻辑。**按月分片 + 明细内嵌**读写模型最简单，单文件也就几十到几百 KB。

## 7. 踩坑清单（按发生概率排序）

1. **隐私协议没配就调相机/选文件 → 接口直接失败**。必须先在公众平台配好《用户隐私保护指引》，勾选"摄像头""相册""文件"。
2. **`wx.scanCode` 在开发者工具里模拟不了**，必须真机调试。
3. **临时文件路径会失效**：`chooseMessageFile` 返回的路径只在当次会话有效，**必须立刻 readFile 或复制到私有目录**，不能存下来下次再用。
4. **`chooseMessageFile` 的 `extension` 过滤**：S2 真机已验证可用（XML/OFD/PDF 均保留原始文件名）。但前提是**以「文件」消息发送**；发成图片会被微信重命名成 32 位 hex 且无扩展名，过滤必然失效。兜底仍是 `type:'all'` + 自己判后缀。
5. **私有目录不是无限的**（约 200MB）。30 天 TTL 必须真的执行，攒满后写入直接报错。
6. **`wx.setStorageSync` 单 key 上限 1MB、总量 10MB**，台账绝不能塞进去。Storage 只放配置和筛选条件。
7. **卸载小程序 / 清理微信缓存会连私有目录一起删掉**。导出是唯一保险，别省略。
8. **`getFileInfo` 的 `digestAlgorithm` 只支持 md5 / sha1**，别指望 sha256。去重键用 `md5 + size` 足够。
9. **金额浮点误差**：全程用整数分，只在显示层除 100。
10. **XML 编码**：数电票一般是 UTF-8，但老系统可能 GBK。`readFile` 不支持 GBK，只能读成 `ArrayBuffer` 自己转。
11. **体验版改了代码要重新上传**，不是自动更新；看到旧版本先怀疑这个。
12. **每个页面必须同时有 `.js/.json/.wxml`**，缺 `.json` 会报 `[app.json 文件内容错误] ... 缺少 .json 文件，无法注册为页面`，表现是导航栏正常但页面全白。新增页面时一并建 `.json`（哪怕只写 `{}`）。

## 8. 已定决策（2026-11-16）

| 决策 | 结论 | 影响 |
|---|---|---|
| **D1 发布策略** | **只自用，开发版 / 体验版** | 跳过审核、ICP 备案、类目；仅体验成员可访问 |
| **D2 OCR** | **砍掉** | M4 整体取消；只保留扫码 + XML/OFD 两条路 |
| **D3 原件存储** | **本地私有目录，30 天 TTL** | 云开发整套移除，架构收敛为纯端侧 |

### 存储策略（D3 确定后）

| 数据类型 | 位置 | 保留期 | 说明 |
|---|---|---|---|
| 发票原件 | `USER_DATA_PATH/invoices/files/` | 30 天 | 私有目录，约 200MB 上限 |
| 结构化记录 | `USER_DATA_PATH/invoices/ledger/*.json` | 6–12 个月 | 按月分片 |
| 配置 / 筛选条件 | `wx.setStorageSync` | 永久 | 只存小数据 |

**收益**：无云开发、无云函数、无计费；发票数据不出手机，与最初"仅供自用、本地归档"的定位完全一致。

**代价**：数据只在这一台手机上。换机、卸载、清缓存都会丢。**导出因此从"可选"变成"必备"**，而且必须做成一步能完成的动作，不能藏在设置二级页里。
